# Changelog

All notable changes to MOC Source are documented here.

## [Unreleased]

### Extension
- Added: GWP (Gift-With-Purchase) threshold-aware Pick-A-Brick cart splitting in Projects (Cart Jigsaw). A new project-level "GWP threshold $" field (Project Setup) makes the existing overflow mechanism threshold-aware instead of purely a lot/qty-limit safety valve — when saving to a Pick-A-Brick cart, each destination cart now fills toward the configured dollar amount (combined PAB+STD total) before spilling to the next, in addition to the existing hard 200-lot / 999-qty-per-lot caps, which always take precedence and are never violated by the threshold logic. Fill order is largest-lot-value-first (a first-fit-decreasing heuristic, not an exact bin-pack solve) and deliberately never splits a lot's quantity across carts for dollar-threshold reasons — only the pre-existing 999-qty-per-lot rule still forces a split.
- Changed: `pab-only`/`bap-only`/`pab-overflow`/`bap-overflow` roles, present in the Setup UI since Multi-cart projects (v0.4.8) but never functionally wired to anything beyond display labels, now drive real channel-specific routing. A project with no Main cart configured can route PAB and STD lots independently through `pab-only`/`bap-only` as their respective primaries, with `pab-overflow`/`bap-overflow` (or a shared `overflow`) as their spillover chains. Added single-cart-per-role enforcement (demote-on-change) for `main`, `pab-only`, and `bap-only` in Setup, matching the existing Main-role enforcement — a second row claiming one of these roles was previously silently unreachable.
- Changed: `showLegoSaveDiff()` (the "Save to Cart ↓" confirmation modal) is now destination-plan-driven instead of single-cart-with-an-overflow-bolt-on. It computes a full multi-cart placement plan up front (`planLegoDistribution`/`resolveLegoDestinationChains`/`fillChannelIntoChain`) and renders one Added/Removed/Changed diff section per destination cart actually touched, each showing its own lot count and dollar total — collapses to the same single-section view as before for projects with just a Main cart and no threshold configured (verified byte-identical behavior for that case). The two previous buttons ("Replace Cart" / "Save + Create Overflow Cart") are unified into one save action.
- Added: a real capacity-exhaustion warning. If every configured cart for a channel is genuinely full at the 200-lot hard limit, save is now blocked with an explicit message ("Every configured cart is at the 200-lot limit — N Bestseller lots have nowhere to go") and a link to Project Setup, instead of the prior behavior of silently merging overflow into a configured cart with no recheck against the limit at all — a real latent bug fixed as a side effect of building genuine per-cart fill tracking. The no-overflow-configured auto-create fallback (an uncapped, threshold-less catch-all cart) is unchanged from before.
- Added: the post-save toast now reports each affected cart's lot count and dollar total (and whether it cleared the configured GWP threshold), instead of a generic "N lots routed" message.

The other 2 mismatches (`"Pearl Dark Gray"`, `"Rose Pink"`) have no equivalent `bl_id` in `colors` at all — a real, separate gap in that table, left unmatched rather than guessed at.

Ran for real: 4,342 of 4,658 candidate part_nos filled, 4,506 new rows, confirmed correct via `bl_part_catalog` names that literally embed the element_id (e.g. "Sticker Sheet for Set 40595 - (10104819/6452641)" for element `6452641` → `40595stk01`). ## [Backend] — 2026-07-21

### `last_used_year` backfill accuracy + Rebrickable bulk API robustness
- Added: `scripts/backfill_last_used_year.py` now floors `last_used_year` at the current year for any part_no with an element currently in-stock somewhere on PAB. Rebrickable's `year_to` only advances once it's catalogued a *set* released this year containing the part, which lags real-world PAB availability by months for an in-progress year — confirmed live: ~1,100-1,400 parts currently in-stock on PAB still showed a stale/prior-year (or entirely absent) `last_used_year` before this fix. Never lowers a value Rebrickable already reported; also resolves still-in-production molds too new to have any Rebrickable record at all.
- Fixed: the bulk `/lego/parts/` endpoint's default `page_size` (100) was being silently hit on every call — previously mistaken for a hard 100-item ceiling on the endpoint itself, when it's actually just a pagination default that truncates without error unless `page_size` is passed explicitly. Confirmed live: 1,000 part_nums + `page_size=1000` returns all matches in one call, no pagination needed.
- Fixed: `_get_with_retry()` (`scripts/_rebrickable_lookup.py`) previously only retried HTTP 429 — any 5xx or network exception was silently abandoned with zero retry. Added retry-with-backoff for both.
- Fixed (the real regression root cause, found via direct reproduction against production data): chunking the bulk `/lego/parts/` calls by a fixed item count let real URL length swing wildly depending on content — part_num strings vary a lot (`"3639"` vs `"973pb1782c01"`), so nominally-identical 1,000-item batches ranged from 8,565 to 16,044 characters in one real run. Some intermediate proxy/edge rejects overly long requests outright with an instant HTTP 520 (~0.2s, not a backend timeout) — reproduced directly: the exact same 1,000-item chunk (16,044 chars) failed every time; split into two ~8,065-char halves, both succeeded; a 13,616-char chunk elsewhere in the same run succeeded fine. Real cutoff sits somewhere in 13.6-15.3KB. `_chunk_by_length()` now batches by a conservative 10,000-character budget instead of a fixed item count, so any chunk stays safely under the limit regardless of content. This bug briefly regressed a live run's unresolved count from 58 to 5,814 (reproduced 3 times before being root-caused and fixed) — no data was corrupted, since unresolved parts are skipped without writing, leaving prior good values untouched.
- Fixed (found immediately after the previous fix, reproduced twice): `_chunk_by_length()` only capped by character length, no item-count cap — short part_nums (`"4429"`, `"52024"`) pack tight enough that the 10,000-char budget alone permitted well over 1,000 items per chunk, but `page_size` was still sent as `min(chunk_size, MAX_PART_NUMS_PER_CALL)`, silently re-truncating the same way the very first `page_size` bug above did, just via chunk count instead of the endpoint's own default. Now caps both character length and item count.
- Added: `backfill_last_used_year.py` now retries via `resolve_element_via_rebrickable()` for anything the bulk pass found zero record of at all. A stored rb part_num can 404 against the bulk endpoint even though the element_id is still perfectly valid — Rebrickable renumbers/consolidates print variants over time (confirmed live via Rebrickable's own part changelog: `92456c10pr0241` → `92456c25pr0001`, renamed 2026-07-10, after our local `elements.csv` snapshot was taken). The element_id stays stable across renumbering, and the per-element response conveniently includes `year_from`/`year_to` in the same call, no second round-trip needed. `resolve_element_via_rebrickable()` now returns those fields. Final verified run after all five fixes: **`Resolved: 41,398 (all of them), unresolved: 0`, 3m27s** — 100% coverage of the reachable pool, up from 58 permanently-stuck parts before. This also organically resolved a long-standing individual holdout (`100588pat0001pr0002`, Rebrickable's current record for that element has no BrickLink translation but does have year data) without needing any manual override.

### Closing the bricklink_mappings coverage gap (~52,528 real BrickLink parts with zero mapping at all)
- Added: `scripts/download_rebrickable_data.py` + weekly re-run of `import_rebrickable.py` against fresh Rebrickable CDN data (`parts.csv.gz`/`elements.csv.gz`/`colors.csv.gz`), replacing a hand-maintained static snapshot that had never been re-run automatically. Rebrickable keeps adding BrickLink translations to its own catalog over time, so a stale snapshot means missing translations Rebrickable has already resolved on their end — no amount of resolution logic downstream can fix that, only a fresher snapshot can. Also consolidates two previously-divergent `elements.csv` copies (`import_rebrickable.py`'s and `backfill_last_used_year.py`'s, separately hand-refreshed and drifting out of sync) into one canonical `/opt/mocsource/data/rebrickable/` location. First real run: **176 new `lego_elements` rows, 183 new `bricklink_mappings` rows**, from fresher data alone.
- Added: `scripts/reverse_map_bl_catalog.py` for BrickLink parts Rebrickable's own catalog never indexed under any numbering at all — Fix A above can't help there, since it depends on a translation already existing. Uses a confirmed-live, undocumented `bricklink_id=` reverse-lookup filter on Rebrickable's bulk `/lego/parts/` endpoint (single-value only, one API call per candidate, no bulk form exists) plus `/lego/parts/{num}/colors/` to get real `element_id`s for a match, since `bricklink_mappings` is keyed on `element_id` not `part_no`. Resumable/batched like `fix_rebrickable_part_nos.py` (the full ~52,528-part backlog is ~17.5 hours of API time at 1 req/sec, infeasible as a single pass) via a new `bl_catalog_gap_fixes` tracking table, prioritizing plain parts (6,985) over printed/decorated ones (45,693) — printed variants are both the largest share of the gap and the class where Rebrickable/BrickLink numbering diverges hardest, so they're the least likely to resolve per attempt.
- Fixed (found in first real batch run): `bricklink_mappings.element_id` FKs to `lego_elements`, but the reverse-lookup path pulls `element_id`s live from Rebrickable's API, which can include ones never in the local `elements.csv` snapshot at all — a real `ForeignKeyViolation` on a live element. `resolve_element_via_rebrickable()` now also returns `design_id` (already free in the same response) so the script can insert into `lego_elements` first, matching `import_rebrickable.py`'s own two-step pattern. Verified: re-ran the exact batch that crashed, completed clean, 7 real rows created including the element that originally failed.

All 17 resolved cleanly via BrickLink's own `item_mapping` endpoint on a fresh attempt.

## [Backend] — 2026-07-19

### PAB stock-status volatility tracking
- New tables `lego_element_stock_monthly` (per element/region/month: `to_in_stock_count`/`to_out_of_stock_count` directional flip counters, `seen_in_stock`/`seen_out_of_stock` booleans) and `lego_element_stock_state` (per element/region: `currently_in_stock`, `last_seen_in_stock_at`) — `region` buckets by the existing `LOCALE_GROUPS` keys (na/eu/kr), not raw locale, since stock is already confirmed identical across every locale within a group. Deliberately event-based, not a day-by-day accumulator: most elements flip 0-1 times a month, and directional flip counts plus "seen this month" flags are enough to extrapolate rough in-stock/out-of-stock duration without the complexity (and correctness hazards around month-boundary crossing) a persistent daily cursor would add.
- Rows are created lazily, only on a real PAB observation — an element never seen on PAB (e.g. a mold discontinued decades ago) never gets a row in either table, at zero storage cost. "Not in stock, last seen N/A" is the default applied at the query layer when no row exists, not a materialized row pre-seeded for the full `lego_elements` universe (which covers Rebrickable's entire bulk-imported catalog, the large majority of which has never touched PAB).
- `scripts/scrape_pab.py`: new `record_stock_events()` helper, hooked into the two write paths that touch `in_stock` in a way that can be attributed to a single representative locale — `write_prices()` and the `MARK_STALE_PRICES_OOS` "left the catalog" sweep (which gained a `RETURNING element_id` clause). The third write path (OOS-mode sibling-locale propagation) is deliberately *not* hooked — the representative locale's own transition is already recorded before its siblings are touched in the same run, so hooking it too would double-count the same real-world event through every sibling locale. Only the 3 representative locales (`en-us`/`de-de`/`ko-kr`, via a new `LOCALE_TO_GROUP` reverse mapping) ever drive writes to either table, for the same reason.
- Verified against the real dev DB inside a rollback-only transaction (never committed): first observation, a real flip, a same-value re-write (must not double-count), the `MARK_STALE_PRICES_OOS` path, two flips accumulating correctly across separate calls, non-representative-locale exclusion via the actual `write_prices()` code path, and the state table's "no row = default" behavior.
- No API endpoint or extension surfacing yet — this pass is data-collection only, per explicit scope.
- Deployed to production 2026-07-20 (one day after merge — `ansible-playbook site.yml` wasn't re-run until this date) and verified live: a manually-triggered `mocsource-scrape-pab-oos` run correctly wrote first-observation rows to both tables for a real element (4211525) — `na` region seeded out-of-stock (`currently_in_stock=false`, `last_seen_in_stock_at` NULL, matching live PAB), `eu`/`kr` seeded in-stock, all three correctly classified as first observations (0 flip counts) rather than false flips.

## [0.4.18] — 2026-07-18

### Extension
- Fixed (actual root cause): every Wanted List / Cart detail page has been permanently unable to load PAB prices since v0.4.17. That release's Project-detail listener-stacking fix accidentally also touched `attachDetailListeners` (a completely unrelated function used by all list/cart detail pages), converting a working `content.addEventListener("click", ...)` call into `addClick(...)` — but `addClick` is only defined as a local helper inside `renderProjectDetail`, not here. Calling it threw `ReferenceError: addClick is not defined` on every single page visit, which aborted `renderDetailView()` — and since that call happens *before* `renderListDetail`'s PAB-price fetch loop, the fetch loop never ran at all, leaving every row frozen at its initial "…" placeholder. (Confirmed via `git log -p` showing the accidental find-replace, and by reproducing the exact call chain in Node to verify the fetch never fires once the throw happens.) Gave `attachDetailListeners` its own cleanup-tracked `addListener`/`addClick` helpers (same pattern as `renderProjectDetail`'s, since this function has the identical repeated-call-on-persistent-container structure) and converted its other two direct `content.addEventListener` calls to use them too, so they stop stacking across re-renders as well.
- Hardened (real but secondary): `renderListDetail` and the Project pool section each fetch every part's PAB price in parallel via `Promise.all`, which fails the whole batch if even one `chrome.runtime.sendMessage` rejects (e.g. a transient MV3 message-channel hiccup). Switched to `Promise.allSettled` so one bad fetch can't block the rest of a page's prices from rendering. This wasn't the cause of the "stuck at …" reports above (the `addClick` crash was), but it's a legitimate robustness gap worth closing regardless.
- Changed: standardized price rounding across the extension. User-facing prices now always show exactly 2 decimals — the BrickLink-page "below PAB"/"BL avg" caption dropped from 3 decimals, and the Cart Jigsaw SPA's Store Price columns (which previously showed BrickLink's raw scraped text verbatim, e.g. `$0.0812US`) now parse and format to `$X.XX`. Cart cost calculations still sum true, unrounded per-item prices as before (no change there — they already did this correctly) but the final "what you'll pay" totals (LEGO cart total, BrickLink cart total incl. shipping, Project Grand Total) now round *up* to the next cent instead of to the nearest cent, via a new `ceilToCents()` helper, so a total is never shown lower than what the real sum comes to. Per-channel subtotals and savings/delta figures (PAB Savings, "switch to save ~$X", Store Savings Scanner) are unaffected — still plain nearest-cent display, since they're informational breakdowns/estimates, not a standalone amount owed. Also widened `content.js`'s `scrapeRowPrice()` regex, which previously truncated BrickLink's own displayed price to exactly 2 decimals before using it in the "beats PAB" comparison — bulk lots with sub-cent per-unit pricing were being compared against a pre-truncated number; now compares against BrickLink's actual full precision.
- Fixed: an unrelated crash found while touching this code — transferring a part from a LEGO cart to a Wanted List stored its PAB price as a string into the new part's `maxPrice` field, but the Wanted List page later calls `.toFixed(2)` on `maxPrice` assuming a Number, throwing a `TypeError`. That PAB price was never a meaningful "max price" for a Wanted List entry in the first place, so the field is now omitted entirely on this transfer path instead of being reformatted.
- Fixed (data-integrity bug, not just display): `content.js`'s `collectCartParts()` scrapes the full text of BrickLink's own price cell into `storePrice` for each cart lot, but only stripped our own `.moc-source-badge` element first — not the `.moc-source-verdict-caption` element (the "▼ below PAB $X and BL avg $X" text) that `injectBadge()` also appends into that same cell. Any row that already had our comparison caption showing on the page when a cart was saved/imported got that caption's text scraped straight into `storePrice`, corrupting it. This reached more than display: `parseStorePrice()` (which strips non-digit characters then parses a float) fed the corrupted string into Auto Allocate's BL-vs-PAB cutover decision, the "select cheaper" buttons and Savings Scanner's bulk move/remove actions, and — most seriously — the live BrickLink cart write-back (`showBlCartSave`/`applyBlCartWriteback`), which re-finds a cart row by **exact string equality** against the stored value; a mismatch there silently no-ops a quantity change or removal while the UI still reports success. Added the missing strip to all three affected sites (`collectCartParts`, `applyBlCartWriteback`'s `findArticle`, and `scrapeRowPrice`, which has the same gap via a different helper feeding "Fill Wanted Qtys"). This fix is forward-only — data already saved before this fix stays corrupted until you click "↻ Refresh" on that cart; Auto Allocate only runs once per project, so re-run it manually afterward if you suspect a past allocation used bad data.
- Added: a real "X% below/above PAB" indicator on the Cart Jigsaw Store Price columns (`buildAllocRows`, `buildCartRow`), computed fresh at render time from the already-known store/PAB prices via a new `pctVsPab()` helper — a deliberate, always-correct replacement for the percentage that used to appear only as an accidental side effect of the leak bug above (that was BrickLink's own bulk-discount indicator, incidentally scraped into the same cell, not something we computed).
- Hardened (BL cart write-back): two more issues found by inspecting real saved data. First, BrickLink's own price cell can independently corrupt `storePrice` on discounted lots even after the caption-leak fix above — its markup wraps the current price, the struck-through "was" price, and the discount % all in the same `div.price-col`. `collectCartParts()` and `findArticle()` (in `applyBlCartWriteback`) now read the `.native-price` element directly instead of the whole cell's text, so only the real live price is ever captured (confirmed against real BrickLink cart-row markup; falls back to the old strip-and-read approach if `.native-price` isn't present). Second, `findArticle()` — the function that re-locates a cart row on the live BrickLink page to apply a saved quantity change or removal — required an *exact string match* on price to succeed at all, which is why any price drift silently no-opped a change while the UI still reported success. It now matches primarily on `partNo`+`colorId` (usually unambiguous on its own), falls back to lot condition (New/Used, already captured but never previously used for this), and only uses price as a last-resort tiebreaker when still ambiguous — never a hard requirement. `showBlCartSave` now threads `condition` through the write-back payload to support this.
- Fixed: a Project's totals for a BL cart could silently drift from the live BrickLink cart / the extension's own standalone Cart detail page while the Project tab was left open. `renderProjectDetail` only re-fetches `carts`/`legoCarts` from storage when the function itself is re-invoked (navigation, back button, a few explicit reload sites) — there was no `chrome.storage.onChanged` listener anywhere, so if `content.js` rescraped a cart's live data in another tab (price changes, shipping resolving from TBD to a real number), an already-open Project tab never found out and kept showing stale numbers, including a manually-typed shipping estimate that should have been superseded by BrickLink's real quote. Added a debounced `storage.onChanged` listener (scoped to `carts`/`legoCarts`) that calls the existing `refresh()` in place — no full page reload, no lost scroll/selection state — cleaned up on re-render via the same pattern used for this view's DOM listeners so it can't stack duplicate listeners across renders.
- Fixed: found while investigating the above — `buildGrandTotal` (the Project's overall total) and `buildBlSection` (each cart's own total, shown directly above it) used different logic to price a part with multiple lots at different prices under partial allocation: one bought cheapest-lots-first (correct, and what the per-row display already reflects), the other just grabbed whichever lot came first in the array and priced the whole allocated quantity at that single lot's price. This could make the Grand Total disagree with the sum of the per-cart totals shown right above it, even with perfectly fresh data. Extracted the cheapest-first distribution into a shared `distributeLots()` helper used by both, so they can no longer disagree about which lots an allocation actually covers.
- Fixed: the remaining ~$0.12 gap between the Project page's Parts total and BrickLink's real total, root-caused from a live cart's actual `outerHTML` — several lots render more than one price in their `div.pricing-box`: a base `.native-price` plus one or more quantity-break tiers (e.g. `$0.03` base, `$0.025[10+]`). When a lot's real cart quantity meets a tier's threshold, BrickLink bills the *entire* lot at that discounted rate, but we'd only ever captured the base price, so every total computed from it (Project's Parts total, the Grand Total, the standalone Cart page's own internal breakdown, the STORE $ column, the %-vs-PAB figure, and `showBlCartSave`'s cheapest-lot decision) silently overstated cost on any bulk-discounted lot. `collectCartParts()` now parses the full tier table per lot (`parsePriceTiers()`, skipping one-time sale/strike-through indicators which are already reflected in the base price); a new `effectivePrice()`/`tierPriceFor()` pair in `index.js` resolves the correct per-unit price from a lot's *real* full cart quantity (not a partial allocation amount — a 13-piece lot that qualifies for a 10+ discount is billed at that rate for all 13, so a partial claim on it fairly gets a proportional share of that same discounted rate, not a re-derived tier for the smaller sub-quantity alone) and is now used everywhere a cart lot's cost is computed or displayed.
- Changed (revises the "Per-channel subtotals... unaffected" note from earlier in this list): every "amount owed" subtotal now rounds *up*, not to nearest, matching BrickLink's own documented policy — their API docs state financial values use 4 decimal places internally and anything with more precision is rounded up, never down (practically: they never let a displayed charge undercut what you actually owe, since fractional-cent payments can't be processed). Verified against a real cart: our raw computed total was `$15.454999999999998` — round-nearest showed `$15.45`, but BrickLink's real total was `$15.46`; `ceilToCents()` on the same raw value produces the exact match. Previously `ceilToCents()` was applied only to final combined totals (LEGO cart total, BL cart total+shipping, Project Grand Total); now also applied to `summaryPanel`'s cart-branch PAB/STD/BrickLink/Total rows, `buildLegoSection`'s Parts/BS/STD rows, and `buildBlSection`'s "Parts:" line — anywhere a subtotal represents real money owed. Savings/delta figures (PAB Savings, "switch to save ~$X", Store Savings Scanner, Wanted List "Max $" rows) are unchanged — still plain nearest-cent, since they're not a charge. Known accepted tradeoff: because each subtotal now ceilings independently from its own raw sum, a set of subtotals can in rare cases not sum to exactly the same-looking combined total (each absorbs its own sub-cent fraction on its own) — not worth the complexity of reconciling further given how small and infrequent this is in practice.
